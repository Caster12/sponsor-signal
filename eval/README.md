# Evaluation set

Target: 200 hand-labeled postings across finance, tech, and consulting, labeled with four categories (see Labels). The spec still lists five; the eval merges `citizenship_or_clearance` into `does_not_sponsor`, pending a spec update.

## Layout

Each collector has a folder, `eval/<name>/` (currently `khushi/` and `vishal/`), with the same layout:

| Path | What it holds |
| --- | --- |
| `meta.jsonl` | One row per posting: id, url, source, industry, sample arm, employer and title as posted. No text. |
| `texts/<id>.raw.txt` | Everything on the page as captured, portal chrome included. This is what the extension would read. |
| `texts/<id>.posting.txt` | Only the employer's job description, cleaned of portal chrome. |
| `postings.jsonl` | Generated by `npm run eval:build` from the two above. Do not edit by hand. |
| `labels/<annotator>.jsonl` | One file per labeler, so labels stay independent. |
| `screenshots/` | Original screenshots, kept so transcriptions can be checked. |

A folder may keep its posting list at `sources/urls.jsonl` instead of `meta.jsonl` (same row format), with raw API responses under `sources/api/`; `vishal/` does this, see `vishal/README.md`. A posting whose row has `raw_page_status: "not_captured"` is description-only: it needs only `texts/<id>.posting.txt`, and its `text_raw` in `postings.jsonl` is null.

`npm run eval:build` builds every folder, then prints quota counts over all of them (split into full-page and description-only) and flags employers over the cap and ids used in more than one folder. Nested batches such as `khushi/description-only/` are not read by the build.

## Adding a posting

1. Work in your own folder. Pick the next id; ids must be unique across all folders (`khushi/` uses `p001`, `p002`, ...). Paste the full page text to `texts/<id>.raw.txt` and the job description alone to `texts/<id>.posting.txt`. Do not edit the wording.
2. Add one line to `meta.jsonl`. `industry` is `finance`, `tech`, or `consulting`. `sample_arm` is `natural` (found by browsing, whatever the label) or `targeted` (found by searching for a rare label).
3. Run `npm run eval:build`.

## Labels

`sponsors`, `does_not_sponsor`, `silent`, `unclear`.

`does_not_sponsor` also covers postings that limit the job by status, such as "must be a US citizen", "US persons only", or a required clearance, because for a student who needs sponsorship the outcome is the same. When scoring, map the model's `citizenship_or_clearance` to `does_not_sponsor`.

Each label row has `id`, `label`, `quote` (the exact words, or `"no sponsorship language found"` for silent), and `notes`.

## Codebook rules so far

- The label comes from the posting's own words. A portal's structured field (for example 12twenty's "Work Authorization") is recorded in `meta.jsonl` as `portal_work_authorization` but does not decide the label.
- Application-form screening questions on the page (for example "Will you now, or in the future, require visa sponsorship to maintain work eligibility?") are not the employer's posting wording and do not decide the label. Record the question in `meta.jsonl` as `page_screening_question`. If the extension quotes it, that is a model error, not the label (see p004).
- "Will not pursue visa sponsorship" is `does_not_sponsor`, even when the same sentence also requires work eligibility.
- Conflicting or ambiguous wording (for example "authorized to work on a permanent basis") is `unclear`. There is no tie-break toward another label.

## Process

- Label independently, without seeing the other labeler's labels or the model's output. Record `seen_model_output` honestly.
- Compute agreement (Cohen's kappa), then adjudicate disagreements together.
- Keep about 60 postings as a dev set for prompt tuning. Report final numbers only on the rest.
- Do not use model output as ground truth.

## Scripts

All run from the repo root; none needs the API except `eval:run`.

| Command | What it does |
| --- | --- |
| `npm run eval:build` | Joins meta and texts into each `postings.jsonl`, prints quota counts. |
| `npm run eval:dev` | Previews the dev set (about 60 postings, seeded, stratified by gold label and industry). `-- --write` saves `eval/dev_ids.txt`; do this once, when the 200 are final. |
| `npm run eval:baseline` | Keyword-search baseline predictions (draft rules, see `scripts/keyword_baseline.mjs`) to `eval/results/baseline.jsonl`. |
| `npm run eval:run -- --split dev --dry-run` | Plans a model run. Without `--dry-run` it calls the model once per posting and writes predictions and `eval/results/gold.jsonl`. Run `--split test` once, after the prompt and baseline are frozen. |

Score with `python3 score_results.py <gold> <predictions> [<baseline>]` from `eval/khushi/description-only/p011-p100/`. Labels made after seeing model output (`seen_model_output` true) are excluded everywhere.
